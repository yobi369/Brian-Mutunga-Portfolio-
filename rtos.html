ENGINEERING CASE STUDY / 07EMBEDDED SYSTEMS · C / ARM

Real-Time Operating System.
Scheduling research meets kernel engineering.

An independent systems-engineering project combining a discrete-time RMS/EDF scheduling simulator with a separate bare-metal ARM Cortex-M3 kernel prototype. The work focuses on low-level execution mechanisms, task synchronization, deterministic tests, and honest verification boundaries.

C / C11ARM CORTEX-M3RMS / EDFQEMUGITHUB ACTIONS

01 / The engineering problem

Real-time systems require more than selecting the next task. They must coordinate task state, timing events, context transitions, synchronization, and failure handling while making the limits of their guarantees explicit.

This project approaches that problem through two separate surfaces: a scheduling simulator for exploring RMS and EDF policy behaviour, and a low-level Cortex-M3 kernel prototype that exercises embedded mechanisms.

02 / System architecture

TWO RELATED, DISTINCT ENGINEERING SURFACES

The simulator does not run the embedded kernel. It is a discrete-time policy exploration tool. The embedded target uses the Cortex-M exception model: SysTick for periodic tick accounting, SVC for first-task launch, and PendSV for deferred context switching.

03 / Implemented engineering areas

  • Rate Monotonic Scheduling (RMS) and Earliest Deadline First (EDF) simulation.
  • Bare-metal Cortex-M3 startup and exception-based context switching.
  • Task lifecycle, fixed-capacity task management, delays and timed waits.
  • Semaphore and mutex APIs, bounded wait-cycle detection, and prototype priority inheritance.
  • Stack canary and saved-stack-pointer diagnostics, plus fault-category capture.
  • Host-native C regression tests, sanitizers, ARM cross-compilation and QEMU scenario tests.

04 / Verification evidence

The GitHub Actions workflow completed successfully for the engineering showcase change. The associated private CI run retained simulator coverage and embedded verification artifacts. Its QEMU artifact contains actual console logs for the baseline boot/scheduler smoke test, tick-wrap scenario, task-return cleanup, priority-chain behaviour, stack-guard handling, and repeated mutex deadlock checks. Detailed logs can be shared during a technical review.

05 / Limitations and next milestones

Engineering honesty: This is an engineering prototype, not a production-ready or safety-certified RTOS. QEMU behaviour does not establish physical timing, worst-case execution time, hard real-time guarantees, or board compatibility.
  • Bring up the Nucleo-F103RB physically and retain serial/debug evidence.
  • Calibrate the actual clock and SysTick period; measure jitter and context-switch latency.
  • Measure interrupt-disabled duration, stack headroom, flash/RAM margins and fault behaviour under representative loads.
  • Expand state-transition and synchronization assurance tests.
  • Evaluate an MPU-equipped MCU if per-task memory isolation is required.

The current STM32F103RB does not provide an MPU. Stack canaries and saved-stack-pointer checks are diagnostics, not memory isolation. The mutex priority-inheritance policy remains a prototype and is not formally proven.
