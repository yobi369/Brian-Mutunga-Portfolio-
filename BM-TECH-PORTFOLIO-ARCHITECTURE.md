# BM Tech — Technology Portfolio Architecture

## Purpose

BM Tech maintains a portfolio of software products, engineering projects, research prototypes and technology capabilities. A repository is not automatically a commercial product. Each repository must be classified by its purpose, maturity, ownership, customer value and operational readiness before it is promoted publicly.

The current working inventory identifies 54 repositories under the GitHub account. The initial README review covered 37 unique repositories and was not a complete source-code, security or deployment audit. This document is therefore a provisional portfolio map, not a final assessment of every repository.

## Repository classification labels

Every repository should receive one primary portfolio role:

| Role | Meaning |
|---|---|
| Product candidate | A potential standalone product with an identifiable user and problem |
| Service capability | Reusable engineering capability that supports paid client work |
| Internal platform | Shared infrastructure or tooling used by BM Tech projects |
| Research project | Experimental work where learning or technical novelty is the main objective |
| Demonstrator | Proof of concept used to communicate an idea or technical approach |
| Archived / superseded | No longer actively developed or replaced by another repository |

A repository may have secondary tags, but it should have only one primary role to avoid confusing the catalogue.

## Maturity stages

Maturity must be recorded separately from portfolio role.

1. **Concept** — idea or early scaffold; no verified working product.
2. **Prototype** — core concept demonstrated, but important product requirements remain.
3. **Development** — active implementation and testing.
4. **Validation** — structured functional, security, usability and deployment checks underway.
5. **Pilot** — limited real-user evaluation under defined controls.
6. **Launch-ready** — documented acceptance criteria, support, security, recovery, ownership and commercial arrangements have been met.
7. **Live** — operating for its intended users with ongoing maintenance.
8. **Paused / Archived** — inactive, superseded or deliberately held.

A live demo URL alone does not qualify a repository as launch-ready.

## Initial commercial focus

The first portfolio should be deliberately narrow.

### Flagship product: Precious SchoolBooks

- Target: schools and education operators.
- Market: Kenya first, with international expansion only after localisation and market validation.
- Current status: controlled pilot.
- Launch gate: complete production-readiness checks, access-control and tenant-isolation verification, recovery testing, and acceptance by a school accountant before handling live school financial data.

### Second product candidate: Secure Properties

- Target: real-estate operators and property businesses.
- Current status: development candidate.
- Next gate: validate customer problem, define a narrow paid use case, review API and data security, and test a complete user workflow.

### Service capability focus: Cybersecurity & Digital Infrastructure

- Initial capability candidates: infrastructure review, application configuration review, deployment support, access-control review and technical remediation.
- Work must be limited to systems the client owns or is authorised to test.
- Scope, authorisation, exclusions and acceptance criteria must be written down before work begins.

Other repositories remain in the portfolio map until they are reviewed. They should not all be promoted as products at once.

## Repository review scorecard

For each repository, record:

- Repository name and URL.
- Primary division and secondary tags.
- Primary portfolio role.
- Intended user and problem solved.
- Current maturity stage.
- Last meaningful activity and maintenance status.
- Build, test and CI evidence.
- Deployment and operational evidence.
- Security, privacy and data-handling risks.
- External service, hosting and licensing dependencies.
- Documentation and support requirements.
- Potential customer and revenue model.
- Next concrete action.
- Decision: advance, maintain, combine, research, pause or archive.

Do not score a repository highly based only on code volume, visual polish, AI features or a deployment badge. Evidence of a complete user workflow and a real customer problem matters more.

## Selection principles

1. Prioritise customer value and a reachable first market.
2. Prefer one focused, supportable product over several unfinished launches.
3. Reuse internal platforms and service capabilities where this reduces delivery cost.
4. Keep research projects visible as engineering work without presenting them as commercial products.
5. Combine overlapping repositories only after reviewing their code, licences, history and dependencies.
6. Preserve repository ownership and history; do not delete or merge projects merely to simplify the public catalogue.
7. Publish only claims supported by current evidence.
